# Methodology

## Purpose
Develop portable detection logic, test it against identified telemetry, document false-positive trade-offs, and communicate residual detection gaps.

## Current status
This repository is a runnable scaffold. The bundled fixtures only test local code paths. No real dataset has been acquired in this generated project, and no claim of real-world detection performance is made.

## Reproducible workflow
1. Select an authorized public dataset or telemetry generated in a controlled lab.
2. Record the dataset citation, version, license, acquisition date, SHA-256, collection method, and limitations in `reports/dataset_register.csv`.
3. Preserve raw files under ignored `data/raw/`; never commit sensitive or unlicensed data.
4. Normalize source fields to the documented detection schema with a versioned script.
5. Select techniques based on observed telemetry and a clear hypothesis; do not assume a technique is detectable from unrelated logs.
6. Validate Sigma syntax and field semantics. Run `sigma check` where available; use a compatible backend for correlations.
7. Record true-positive matches, false positives, missed detections, and limitations. Every claim in reports must reference event IDs or stable evidence locators.
8. Perform at least three tuning passes on at least three rules: document initial false-positive scenario, changed logic, observed effect, and trade-off.
9. Update coverage status only when the rule is tested against relevant data. Separate “rule authored” from “behavior validated”.
10. Peer-review rule quality, ATT&CK mapping, evidence traceability, and operational response steps.

## Evidence classification
- **Synthetic fixture:** made for software smoke tests; not evidence of real attacker activity.
- **Public sample:** genuine published event sample; context and representativeness may be limited.
- **Lab telemetry:** generated by a documented, authorized test on a controlled host; state exact tool/test ID and configuration.
- **Production telemetry:** requires explicit authorization, handling controls, and data minimization.

## Limitations
The local harness evaluates a small Sigma subset and does not support correlation semantics, backend field mapping, aggregation windows, or SIEM query execution. Correlation rules are examples only until validated in a compatible backend.
